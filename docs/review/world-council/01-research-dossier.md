## 1. Tauri 2 mobile and content-heavy apps

- **WebView per platform [P]** https://v2.tauri.app/reference/webview-versions/ : Windows = WebView2 (Chromium, self-updating, preinstalled on Win 11); macOS and iOS = WKWebView, version follows the OS (unsupported OS versions get no WebKit updates); Android = system WebView, **not bundled**, version depends on the device's WebView provider, and some images use a different provider. Implication: three engines (WebKit, Chromium-system, Chromium-WebView2) and no way to pin a version on mobile; Android behaviour must be tested on old devices.
- **Mobile maturity.** InfoWorld/AlternativeTo (2024, [S]) reported Tauri's own statement that 2.0 over-promised "mobile as first-class citizen" and that not all official plugins work on mobile: https://www.infoworld.com/article/3485804/tauri-2-0-moves-core-functionality-to-plugins.html and https://alternativeto.net/news/2024/10/tauri-2-0-enhances-cross-platform-app-development-with-mobile-support-and-improved-plugins . A May 2026 third-party decision record ([S], one team's view, https://range-day-docs.pages.dev/decisions/Tauri-vs-Capacitor ) says no reliable official camera plugin, push notifications community-only, mobile "closer to alpha". [U]: I found no current (2026) official Tauri statement on mobile plugin coverage; check tauri-apps/plugins-workspace directly.
- **Updater [P]** https://v2.tauri.app/plugin/updater/ : setup steps are desktop-only (macOS/Windows/Linux). On iOS/Android, updates are via the stores (unsurprising, and also required by Apple 2.5.2, see section 8). Web assets can't be hot-swapped on iOS legitimately.
- **WKWebView practicalities [S]** (community guide, Apr 2026): https://takazudo-zudo-tauri.pages.dev/pj/zudo-tauri/docs/mobile/wkwebview-gotchas . Reported: `env(safe-area-inset-*)` is 0 without `viewport-fit=cover`; values can go stale after rotation; `window.innerHeight` does not shrink when the keyboard opens; focus-scroll jumps. Android: `env()` safe-area support gaps, keyboard covering inputs. These are generic WebView issues, not Tauri bugs, and are fixable in CSS/JS but are ongoing per-platform tuning.
- **App Store flow [P/S]** https://v2.tauri.app/distribute/app-store/ : build via `tauri ios build --export-method app-store-connect`, upload with altool/Xcode. [U]: I found **no first-hand 2026 report of a Tauri iOS app's App Review outcome**; only how-to guides.
- **Text selection / clipboard / performance:** [U] no 2026 sources found. Behaviour is whatever the system WebView does (native selection handles, native copy), which is generally mature for text-heavy pages.
- **Production anecdote [S]:** a Jan 2026 newsletter mentions one developer building four mobile apps with Tauri as a stress test, no WebView problems reported in the excerpt: https://jlw-newsletter.pages.dev/jlw-2026-01-26-tauri.html .

## 2. Flutter for the same kind of app

- **Release state [S]:** Flutter 3.47.0 stable on 2026-08-12 (our own memory notes say 3.47.7 is in use). Impeller became default on Windows, Linux and macOS in 3.47 (Metal on macOS, Vulkan on Windows/Linux), AOT shaders, SDF text on desktop: https://startdebugging.net/2026/08/flutter-3-47-impeller-default-renderer-on-desktop/ (opt-out to be removed later; no Windows-specific known issues listed). Android Impeller default on API 29+ since 3.38 and Skia backend removal targeted for Android in 2026 ([S] https://devnewsletter.com/p/state-of-flutter-2026/ ). Official 2026 roadmap [P] https://github.com/flutter/flutter/blob/main/docs/roadmap/Roadmap.md : Android Impeller completion, Wasm to become the web default, multi-window desktop work (Canonical), min. 4 stable + 12 beta releases in 2026, "aspirational, not a guarantee". The roadmap text I read did not mention desktop Impeller; the 3.47 claim rests on secondary coverage: **verify against official 3.47 release notes**.
- **Single renderer:** real, since 3.47 on all five targets except web (web uses CanvasKit/Skwasm). Consequence: pixel-identical layout and text shaping engine across platforms; quality depends on one engine rather than three webviews.
- **List virtualisation / large grids:** Flutter's `SliverGrid`/`ListView.builder` virtualise by design; [U] I found no sourced benchmark for 1,443-image grids. Image memory is managed via `ImageCache` and `cacheWidth/cacheHeight` (from general knowledge, not sourced here).
- **CJK/RTL and selection:** [U] no sourced 2026 evidence. One older engine commit notes CJK glyphs "slightly too fine" (https://flutter.googlesource.com/mirrors/engine/+/refs/heads/fuchsia_f20%5E, old, [S]); SDF text arrived on desktop in 3.47. A package vendor claims selection across many separate `RichText` widgets is a weak point ([S] https://pub.dev/packages/hyper_render, vendor claim). Our own Words/Sword apps are the best local evidence of CJK/ru selection behaviour on Flutter.
- **Accessibility [S/P]:** official docs list VoiceOver/JAWS/NVDA for web ( https://docs.flutter.dev/ui/accessibility/assistive-technologies ); screen-reader voice locale follows `MaterialApp.locale` from 3.38. [U] desktop screen-reader maturity (macOS/Windows native) not established.
- **App size, startup:** [U] no sourced figures.
- **Flutter web:**
  - Size: ~0.9-1.5 MB for Skwasm path vs ~4.2 MB compressed total on the default CanvasKit route in one measurement of the Wonderous demo dated 2026-08-18 ([S] https://www.issoh.co.jp/tech/details/16727/ , https://ecorpit.com/flutter-web-wasm-production-guide-2026/ ); `--wasm` build falls back to CanvasKit without WasmGC.
  - SEO: canvas text is invisible to crawlers; Japanese article concludes Flutter web suits login-gated apps, poor for search-facing first-visit pages ([S]).
  - Share previews: crawlers like Facebook/Slack/X read only static `index.html`; per-route OG tags need prerender tooling (`flutter_prerender`, `esen_seo`), both third-party, tested against Flutter 3.41.2, with open issues questioning SEO trustworthiness ([S] https://pub.dev/packages/flutter_prerender ). Flutter's own FAQ reportedly recommends Jaspr or plain HTML for document-like sites ([U], quoted via flutter_prerender page).
  - PWA/install: [U] not researched with a source.

## 3. Multi-app shared code in Flutter

- **Tooling [S]:** Dart pub workspaces (Dart 3.6+) with Melos 7.x (config now in root `pubspec.yaml`, members use `resolution: workspace`; one `pub get` for all members): https://melos.invertase.dev/getting-started , https://medium.com/@sijalneupane5/flutter-monorepo-from-scratch-2025-going-into-2026-pub-workspaces-melos-explained-properly-fae98bfc8a6e . Glob support for workspace members is reported inconsistently (Dart 3.11 reportedly adds it): **[U], check Dart docs**.
- **Patterns [S]:** `apps/*` + `packages/*`; run tests only for changed packages in GitHub Actions; known drawback: a breaking change in a low-level package hits all apps (https://dev.to/jvivasb20/monorepos-in-flutter-scaling-shared-code-without-losing-your-mind-d22 ).
- **CI/CD [S]:** Fastlane + GitHub Actions release workflows exist for single apps (https://nttdata-dach.github.io/posts/dd-fluttercicd-02-releases ); multi-app parameterisation is DIY. Appditto ships several Flutter apps (Natrium, Kalium, Blaise) with Fastlane on GitLab (https://medium.com/appditto/automate-your-flutter-workflow-using-gitlab-ci-cd-and-fastlane-5872e758165a ). Signing secrets must live outside the repo or be scoped per app. [U]: no public, detailed case study of one team shipping 3+ related Flutter apps from a monorepo with per-app cadence.
- **Feature flags per app, design-system packages, codegen:** [U] nothing sourced beyond general practice. Codegen risk noted in section 7.

## 4. 3D in Flutter, 2026

- **flutter_scene [P]** https://pub.dev/packages/flutter_scene : version 0.24.3 (published "26 days ago" as read; exact date not given); platforms Android, iOS, Linux, macOS, Web, Windows; needs Flutter 3.47 stable or newer, Flutter GPU must be enabled per platform (flag/config; web needs none); Windows/Linux release builds need 3.47.1; **pre-1.0, minor releases may carry breaking changes**. Features listed: glTF import, PBR, IBL, shadows, skeletal/morph animation, instancing, particles, Gaussian splatting, physics, raycast picking, `SceneView` widget, screen-reader accessibility, desktop scene editor with MCP server. Note: earlier search snippets (0.18-0.20, spring 2026) said master channel was required; the current page says stable 3.47 suffices, so the situation moved fast. Treat as young but unusually active.
- **Walk-through, panorama, figures:** flutter_scene's feature list covers meshes, skeletal animation, picking. [U] no public Flutter example of an ark/tabernacle walk-through or a Bible 3D app; no 3D Bible/education Flutter app found (search returned only 2D Flutter Bible/church apps: Elisha, Euvic scripture-learning, Lead Small).
- **WebView + three.js/Babylon [S]:** works; community reports of three.js in `flutter_inappwebview` (cache caveat, GLB from CDN OK, JS injection for data): reddit snapshot April 2026 https://reddit.sentinel-team.org/posts/1sqfdte/snapshots/2026-04-21T08%3A23%3A25.462581Z ; `offline_webview` package for local serving (https://pub.dev/packages/offline_webview ). Same three.js code would also run in the existing TS site and Tauri, which is a reuse argument for keeping 3D in web tech. [U] performance parity with native on low-end Android WebView.
- **Embedding engines [S]:** `flutter_unity_widget` (Unity as a Library; 271 open issues listed, version info inconsistent: https://fluttergems.dev/packages/flutter_unity_widget/ ). `flutter_godot` 0.0.3 is Android-only with known bugs (hot-restart display failure); `libgodot` 0.0.1 macOS, docs pending (https://pub.dev/packages/flutter_godot , https://pub.dev/packages/libgodot ). Immature.
- **Not researched with sources:** three_dart, model_viewer_plus (WebView-based wrapper around Google model-viewer, from general knowledge), Flame, Rive 3D (searched; no result on Rive 3D: **[U]**).

## 5. Alternatives

- **Compose Multiplatform [S]:** iOS stable since 1.8.0 (May 2025); desktop JVM stable; Web (Wasm) beta; latest named 1.11.1 per an Aug 2026 Japanese guide ([S] https://www.issoh.co.jp/tech/details/16032/ , https://www.neowin.net/amp/jetbrains-brings-compose-for-ios-to-stable-with-compose-multiplatform-180-release ). Would mean new Kotlin codebase, no reuse of Words/Sword Dart. [U] CJK/RTL, 3D, store-size data.
- **React Native / Expo [S]:** SDK 55 (RN 0.83) is New Architecture only; migration advice: move to New Arch on SDK 54 first (https://expo.dev/blog/upgrading-to-sdk-55 ). Bible-publisher evidence: HarperCollins Christian (Bible Gateway) and Ligonier postings describe React Native + Expo (https://careers-harpercollins.icims.com/jobs/4799/senior-mobile-app-developer/job , https://careers.ligonier.org/postings/senior-software-developer-mobile-8a7885a89d02e553019d21694b451910 ). YouVersion publishes an RN/Expo SDK (iOS-only so far) and a React SDK (https://github.com/youversion/platform-sdk-reactnative ), but [U] what YouVersion's flagship app uses; a posting suggests Flutter for the Android Bible App ([S] builtin.com Senior Flutter Software Engineer listing, unverified link to YouVersion). RN has no first-party Windows/macOS parity with Tauri-level simplicity ([U], not researched).
- **Shopify reversal [P-ish]:** InfoQ, Sept 2026: Shopify moving flagship apps from React Native to Swift/Kotlin, citing coding agents lowering the cost of native duplication; Shop app rebuilt in 12 weeks by six engineers; startup -23% iOS, -50% Android. Critics: baselines were old RN architecture; OTA update difficulty. https://www.infoq.com/news/2026/09/shopify-drops-react-native/ . Relevant as a data point on the "agents make per-platform native cheaper" thesis, from a team with large budget and 300+ screens; not directly transferable to a small ministry team shipping four platforms.
- **Capacitor / Ionic:** Apple forum thread shows a Capacitor app with native location, Swift plugin and clipboard still rejected under 4.2 ([P-seen via search] https://developer.apple.com/forums/thread/812889 ). [U] Capacitor 8 status.
- **.NET MAUI [S]:** MAUI 10 supported to 2027-05-11 per Microsoft policy page; community doubts about investment; no Linux/Web ( https://dotnet.microsoft.com/en-us/platform/support/policy/maui , https://github.com/dotnet/maui/discussions/29647 ). No migration story found.
- **Native per platform:** only evidence is Shopify above. For World, that would be four codebases (Swift, Kotlin, Windows, web).

## 7. AI coding agents: Flutter vs TypeScript

- All sources are opinion or vendor material [S]; no rigorous benchmark covering Claude Code/Codex on Flutter. Claims: TypeScript/React dominate training data, so more reliable output (https://expo.dev/articles/choosing-a-mobile-stack/which-mobile-stack-for-ai-coding-agents , vendor with interest); Dart concise and Flutter's analyzer/test culture helps (Flutter-focused blogs); agents often skip `build_runner` after adding `@freezed`/`@riverpod` classes, leaving the build broken (https://dev.to/sayed_ali_alkamel/vibe-coding-flutter-the-senior-devs-honest-take-1k0f ). Shopify says separating logic from UI lets agents test most logic without simulators (InfoQ link above).
- Local, first-hand evidence from our own memory notes (not web): concurrent `flutter test` runs produce phantom failures; local analyze differs from CI analyze (newer Flutter in CI). Treat these as known operational costs for agents on Flutter.
- Flutter Scene advertises an MCP server and agent skills for its editor ([P] pub.dev page above), so 3D tooling is already agent-oriented.

## 8. Licensing and store policy

- **Apple [P]** https://developer.apple.com/app-store/review/guidelines/ (fetched; no "last updated" date visible in extract): 4.2 "features, content, and UI that elevate it beyond a repackaged website"; 4.2.2 no apps that are primarily web clippings or collections of links; 2.5.2 apps must be self-contained and not "download, install, or execute code which introduces or changes features or functionality"; 2.5.6 browsing apps must use WebKit; 4.7 permits HTML5/JS mini apps with conditions (index of content, no extra native API exposure). 4.2 applies to any framework; the Capacitor forum case shows native plugins alone did not satisfy a reviewer. Practitioner advice: offline behaviour, native icon/launch screen, safe-area correct layouts ([S] https://takazudo-zudo-tauri.pages.dev/pj/zudo-tauri/docs/mobile/app-store-review-4-2 , https://www.mobiloud.com/blog/app-store-review-guidelines-webview-wrapper ). A Flutter app is not exempt from 4.2 but is not a "wrapper" by construction. World's picture-plus-reader content is original content, which is what 4.2 asks for.
- **Google Play [S]:** only the 2024 Spam and Minimum Functionality update was found (effective 2024-08-31; targets static text/PDF-only and non-functional apps): https://www.sammobile.com/news/google-remove-low-quality-apps-play-store/ . [U] any WebView-specific current policy text.
- **Microsoft Store:** Flutter: package as MSIX (`msix` pub package), Partner Center account, WACK validation ([P] https://docs.flutter.dev/deployment/windows ). Tauri MSIX/Store packaging: [U] not found; Tauri docs list Windows installers (NSIS/MSI) but Store route not verified.
- **Content licensing** is unaffected by stack (AI-generated pictures; text licences are separate and covered in memory notes).

## What the evidence says (one page)

Scale: 1 = best/lowest cost, 4 = worst. Rankings are my reading of the sources above, many [S]; confidence low where noted.

| Criterion | A Tauri+web | B Flutter all (incl. web) | C Flutter native + TS web + WebView labs | D Other (best of: KMP/CMP, RN) |
|---|---|---|---|---|
| Long-term release cost (4 platforms) | 2: one codebase, but 3 webview engines, Tauri mobile plugin gaps, 4 shells to keep current | 2: one codebase, but Flutter web weak for share/SEO so a second site is likely anyway | 3: two codebases (Dart + TS) but reuses Words/Sword packages and CI | 4: new stack, new CI; no reuse of existing Dart |
| Extensibility (features, more apps) | 3: web code is shareable across apps, but Words/Sword are Flutter so a second shared base | 1 (if all apps are Flutter): one language, one design system, melos workspace | 1-2: shared Dart packages with Words/Sword; web layer separate | 3-4 |
| Quality ceiling per platform | 3: depends on OS webview versions; fine for reading UIs | 1-2: one renderer; Impeller default on all native targets since 3.47 (secondary source) | 1-2 native; web layer is mature HTML | 2 (CMP desktop/iOS stable; RN native feel) |
| 3D future | 1-2: three.js/Babylon native to the stack, offline-capable, same code as web | 3: flutter_scene pre-1.0 (0.24.3) but fast moving, on all platforms; no known walk-through/Bible precedents | 2: choose per feature: flutter_scene or WebView three.js reusing the TS site | 3: separate story per stack |
| Cost to reach store quality | 2: already built; unknown 4.2/UX risk on iOS since no Tauri review reports found | 3: rewrite of 1,443-picture reader, search, i18n, offline | 3: native rewrite, existing web assets reusable | 4 |
| AI-agent friendliness | 1-2: TS dominant in training data, fast iteration; no codegen chain | 2: analyzer/tests good; codegen and test-concurrency pitfalls | 2-3: two languages to maintain | 3 |
| Risk | 3: Tauri mobile maturity unproven by public evidence, Android WebView variance | 2-3: web SEO/share, text selection unknowns; Flutter pace is steady | 2: sum of two stacks; proven locally by Words/Sword | 4 |

Reading the evidence:
- Nothing sourced shows Tauri mobile as failing; equally, nothing sourced shows a shipped, reviewed Tauri iOS content app. Its main documented risks are system-WebView variance (esp. Android) and thin mobile plugin coverage.
- Flutter's native-app story is strongest since 3.47 (single renderer including desktop), and the owner's two existing apps already pay that learning cost. Flutter web is the documented weak spot for share previews/SEO (workarounds exist but third-party), which supports keeping a plain HTML/TS layer for public pages under B or C.
- 3D: flutter_scene is the first credible Flutter-native option but is pre-1.0 with breaking minors; a WebView labs module is feasible and offline-friendly; Unity/Godot embedding is immature. There is no precedent found for a Bible/education 3D walk-through in Flutter.
- Shopify's Sept 2026 reversal is evidence agents lower the cost of per-platform code, but for a large company with a 12-week team effort; it neither supports nor refutes C for a small team.
